## Тестовое задание на позицию Fullstack разработчика (Python + React)

**Вводные:**
1. Здесь представлен MVP проект файлообменника. Он позволяет загружать файлы, проверяет их на подозрительный контент и отправляет алерты;
2. Репозиторий содержит в себе бэкенд и фронтенд части;
3. В обоих частях присутствуют баги, неоптимизированный код, неудачные архитектурные решения.

**Задачи:**
1. Проведите рефакторинг бэкенда, не ломая бизнес-логики: предложите свое видение архитектуры и реализуйте его;
2. (Дополнительно) На бэкенде есть возможность неочевидной оптимизации - выполните ее;
3. (Дополнительно) Разбейте логику фронтенда на слои;

Остальные поля `Settings` (`MAX_REQUEST_OVERHEAD`, `UPLOAD_CHUNK_SIZE`, `SUSPICIOUS_SIZE_THRESHOLD`, `SUSPICIOUS_EXTENSIONS`, `STALE_AFTER_SECONDS`, `RECONCILE_INTERVAL_SECONDS`, `RECONCILE_BATCH_SIZE`) в таблицу не вынесены: у них есть разумные значения по умолчанию в `core/config.py`, в `.env`/`.env.example` они не задаются и переопределяются обычной переменной окружения при необходимости. `MAX_REQUEST_OVERHEAD` (по умолчанию 1 МиБ) — запас поверх `MAX_UPLOAD_SIZE` для грубого барьера по заголовку `Content-Length` (`api/middleware.py`): multipart-конверт (граница, заголовки частей, имя файла, поле `title`) добавляет байты сверх самого файла, поэтому порог барьера — сумма, а не сам `MAX_UPLOAD_SIZE`.

## Архитектура

### Бэкенд (`backend/src`)

```
src/
├── main.py            # сборка FastAPI-приложения: роутеры, CORS, обработчики ошибок
├── api/
│   ├── v1/             # HTTP-роутеры — разбор запроса, вызов сервиса, HTTP-код ответа
│   ├── deps.py          # DI-провайдеры (FastAPI Depends) для сервисов и сессии
│   └── errors.py         # маппинг доменных исключений в JSON-ответы
├── services/           # бизнес-логика: FileService (оркестрация), scanner, metadata
├── repositories/       # единственный слой, знающий SQL/SQLAlchemy
├── domain/             # ORM-модели и enum'ы статусов — общий язык всех слоёв
├── storage/            # FileStorage — протокол + локальная реализация на диске
├── worker/             # Celery: приложение, задачи, реконсилятор зависших файлов
└── core/                # конфиг (pydantic-settings), сессия БД, доменные исключения
```

### Фронтенд (`frontend/src`)

```
src/
├── app/         # Next.js App Router: страница, layout — точка сборки фич в экран
├── features/    # автономный кусок функциональности (api + model + ui): file-list, file-upload, alert-feed
├── entities/    # доменные типы, общие для нескольких фич (File, Alert)
└── shared/      # переиспользуемая инфраструктура без домена: http-клиент, конфиг, форматирование, поллинг-хук
```

### Правило направления зависимостей

Бэкенд: **`api → services → repositories → models`**. Роутер не знает про SQL, сервис не знает про HTTP (доменные исключения несут транспортно-нейтральный `kind`, а таблицу «`kind` → HTTP-статус» держит `api/errors.py`), репозиторий не знает про бизнес-правила. Инфраструктура (`storage/local.py`, брокер Celery) спрятана за протоколом (`storage/base.py:FileStorage`), которым владеет вызывающий слой (`services`), а не наоборот.

Шов закрывает сервисный слой, но не транспортный. Подмена локального диска на S3 не потребует правок в `FileService`, но потребует их в маршруте скачивания: `FileStorage.path()` отдаёт `Path` прямо в `FileResponse`, а у объектного хранилища локального пути нет. Понадобится presigned-редирект или `StreamingResponse`.

Фронтенд: **`shared → entities → features → app`**. Слой видит только то, что находится левее него: `shared` не знает о домене, `entities` не знает о фичах, `features` не знают друг о друге напрямую и не импортируют компоненты соседних фич, `app` только собирает готовые фичи на странице.

### Как запускать тесты

```bash
# основной набор — внутри контейнера
docker exec backend env UV_NO_DEV=0 uv run pytest tests/ -v

# тесты отказов — только с хоста, они сами тушат и поднимают контейнеры
cd backend && uv run pytest tests/test_failure_modes.py -v

# тест на память — по умолчанию пропускается, рестарт обязателен
docker compose -f docker-compose.dev.yml restart backend
RUN_MEMORY_TEST=1 uv run pytest tests/test_upload_memory.py -v
```

Три неочевидных момента. `UV_NO_DEV=0` нужен потому, что образ собран без dev-зависимостей. Тесты отказов управляют `docker compose`, поэтому изнутри контейнера не работают. Рестарт перед замером памяти нужен потому, что счётчики cgroup монотонны и сами не сбрасываются — иначе пик от прошлых загрузок замаскирует результат.

### Что было исправлено

Фиксы, не менявшие ответ клиенту: только внутреннее поведение и потребление ресурсов.

- **Загрузка держала файл целиком в памяти.** Потоковая запись (`storage/local.py`) и однопроходные аккумуляторы метаданных (`services/metadata.py`) дают на стократном росте размера файла (3 МБ → 300 МБ) рост кучи процесса `backend` на **0.10 MiB** вместо роста, пропорционального размеру.
- **Три Celery-таски вместо одной.** Цепочка `scan_file_for_threats → extract_file_metadata → send_file_alert` стоила три круга через брокер, шесть SQL-стейтментов и три коммита на файл. Сведена в `process_file` (`worker/tasks.py`): один круг, четыре стейтмента, один коммит.
- **Исключение в середине цепочки оставляло файл в `processing` навсегда**, без единого алерта. Теперь `on_failure` доводит запись до `failed` с `critical`-алертом, а реконсилятор (`worker/reconciler.py`) подбирает всё, что зависло по другим причинам, включая недоставленную задачу.
- **`task_acks_late=False` терял задачи вместе с воркером.** Включены `task_acks_late=True` и `task_reject_on_worker_lost=True`.
- **Result backend копил результаты, которые никто не читал** — задачи ничего не возвращают, файл обновляется прямо в БД. Отключён.
- **`MAX_UPLOAD_SIZE` не был барьером на входе.** Starlette спулил тело на диск до обработчика, и `413` приходил уже после приёма байтов. Чистая ASGI-мидлварь (`api/middleware.py`) отклоняет запрос по заголовку `Content-Length`, не прочитав ни байта тела. Код `413` был достижим и раньше, изменился только момент срабатывания.
- **Сборка фронтенда падала** на `COPY /app/.env.production` — файла не было в репозитории.

### Что изменилось в наблюдаемом контракте API

Задание требует рефакторинг «не ломая бизнес-логики». Наблюдаемое поведение изменилось в шести местах: первые четыре — починка дефектов, последние два — осознанно введённые границы пагинации.

| Что | Было | Стало | Причина |
|---|---|---|---|
| `DELETE /files/{id}` | `500` на любом обработанном файле | `204`, запись, алерты и байты удаляются | у `alerts.file_id` не было `ON DELETE CASCADE`, а алерт есть у каждого файла — удалить было нельзя в принципе |
| `POST /files` при лежащем брокере | `500`, хотя файл уже записан и строка создана | `201`, задачу подбирает реконсилятор | клиент получал отказ на успешно принятый файл, запись оставалась осиротевшей |
| Статус `processing` | наблюдался снаружи между тасками | недостижим: `uploaded` сразу в `processed` или `failed` | три таски схлопнуты в одну, промежуточное состояние больше не коммитится отдельно |
| Пропажа байтов с диска | `failed` + `critical`-алерт | `processed`/`clean` | воркер больше не открывает файл: метаданные посчитаны при загрузке |
| `GET /files`, `GET /alerts` | все строки | первые 100 | добавлена пагинация; фронт `limit`/`offset` не передаёт, для пользователя хвост списка исчезает |
| `?limit=1000`, `?offset=-1` | `200`, параметр игнорировался | `422` | `Query(100, ge=1, le=500)` валидирует границы |

Всё остальное — коды на прочих путях, состав полей, тексты `detail`, сортировка — не менялось. Это держат характеризационные тесты, написанные **до** рефакторинга (`tests/test_api_contract.py`, `test_pipeline.py`). Их ожидания поменялись ровно в одной строке — там, где фиксировался сломанный `DELETE`.

### Что дальше

- **У сканера нет собственного шва.** `scan()` синхронна и получает только имя, размер и MIME; настоящему сканеру (ClamAV, песочница, внешний API) нужны байты, `await` и свои ретраи, поэтому замена заглушки затронет и сигнатуру, и вызов в `_process`. Просится протокол `ThreatScanner` рядом с `FileStorage`.
- **`FileStorage` не закрывает транспортный слой.** `path()` отдаёт `Path` прямо в `FileResponse`; для S3 нужен presigned-редирект или `StreamingResponse`, то есть правка маршрута скачивания. Транспортно-нейтральная форма — `open_stream()`.
- **Воркер не переиспользует `FileService`.** Сервис коммитит сам и самодостаточен, но `worker/tasks.py` и `reconciler.py` работают с репозиториями напрямую, дублируя «сессия → мутация → коммит». Просится общий `UnitOfWork`, одинаково доступный маршруту, задаче и CLI.
