## Архитектура

### Бэкенд (`backend/src`)

```
src/
├── main.py            # сборка FastAPI-приложения: роутеры, CORS, обработчики ошибок
├── api/
│   ├── v1/             # HTTP-роутеры — разбор запроса, вызов сервиса, HTTP-код ответа
│   ├── deps.py          # DI-провайдеры (FastAPI Depends) для сервисов и сессии
│   └── errors.py         # маппинг доменных исключений в JSON-ответы
├── services/           # бизнес-логика: FileService (оркестрация), scanner, metadata
├── repositories/       # единственный слой, знающий SQL/SQLAlchemy
├── domain/             # ORM-модели и enum'ы статусов — общий язык всех слоёв
├── storage/            # FileStorage — протокол + локальная реализация на диске
├── worker/             # Celery: приложение, задачи, реконсилятор зависших файлов
└── core/                # конфиг (pydantic-settings), сессия БД, доменные исключения
```

### Фронтенд (`frontend/src`)

```
src/
├── app/         # Next.js App Router: страница, layout — точка сборки фич в экран
├── features/    # автономный кусок функциональности (api + model + ui): file-list, file-upload, alert-feed
├── entities/    # доменные типы, общие для нескольких фич (File, Alert)
└── shared/      # переиспользуемая инфраструктура без домена: http-клиент, конфиг, форматирование, поллинг-хук
```

### Правило направления зависимостей

Бэкенд: **`api → services → repositories → models`**. Роутер не знает про SQL, сервис не знает про HTTP (доменные исключения несут транспортно-нейтральный `kind`, а таблицу «`kind` → HTTP-статус» держит `api/errors.py`), репозиторий не знает про бизнес-правила. Инфраструктура (`storage/local.py`, брокер Celery) спрятана за протоколом (`storage/base.py:FileStorage`), которым владеет вызывающий слой (`services`), а не наоборот.

Шов закрывает сервисный слой, но не транспортный. Подмена локального диска на S3 не потребует правок в `FileService`, но потребует их в маршруте скачивания: `FileStorage.path()` отдаёт `Path` прямо в `FileResponse`, а у объектного хранилища локального пути нет. Понадобится presigned-редирект или `StreamingResponse`.

Фронтенд: **`shared → entities → features → app`**. Слой видит только то, что находится левее него: `shared` не знает о домене, `entities` не знает о фичах, `features` не знают друг о друге напрямую и не импортируют компоненты соседних фич, `app` только собирает готовые фичи на странице.

### Как запускать тесты

Обычный набор тестов гоняется **внутри контейнера** `backend`, чтобы тесты видели ровно то окружение (БД, переменные), в котором работает приложение:

```bash
docker exec backend env UV_NO_DEV=0 uv run pytest tests/ -v
```

`UV_NO_DEV=0` обязателен: `backend/Dockerfile` собирает образ без dev-зависимостей (`pytest`, `ruff`, `mypy` не нужны в проде), и без этой переменной `uv run` откажется ставить их поверх уже собранного окружения.

Тесты отказов (`tests/test_failure_modes.py`) сами останавливают и поднимают `backend-worker`/`backend-redis` через `docker compose`, поэтому из контейнера их гонять нельзя. Запускаются **с хоста**:

```bash
cd backend && uv run pytest tests/test_failure_modes.py -v
```

Тест на память (`tests/test_upload_memory.py`) по умолчанию пропускается: он заливает файл на несколько сотен мегабайт и меряет прирост кучи процесса `backend` через cgroup, поэтому дорогой и требует `docker compose`.

Перед замером контейнер `backend` нужно перезапустить. Счётчики cgroup (`memory.stat`) монотонно растут с момента старта процесса и сами не сбрасываются, поэтому без рестарта пик от предыдущих загрузок (в том числе ручных, через UI) замаскирует результат. Включается явно:

```bash
docker compose -f docker-compose.dev.yml restart backend
RUN_MEMORY_TEST=1 uv run pytest tests/test_upload_memory.py -v
```

### Почему Celery остался

После оптимизации фоновая обработка файла (`worker/tasks.py::_process`) — это два `SELECT` (файл, проверка дубликата алерта по уровню), один `UPDATE` и один `INSERT` на один коммит. Брокер под такую нагрузку формально избыточен. Но убрать его нельзя по двум причинам:

1. `POST /files` наблюдаемо асинхронен: ответ `201` приходит с `processing_status: "uploaded"` и `scan_status: null`, до того как обработка завершилась, а результат клиент узнаёт отдельным `GET`/поллингом. Синхронная обработка внутри запроса изменила бы этот ответ: `processing_status` пришёл бы сразу `processed`/`failed`, а `scan_status`/`metadata_json` — уже заполненными.
2. Проверка расширения (`services/scanner.py`) — заглушка на месте настоящего сканера (ClamAV, песочница, внешний антивирусный API), где счёт идёт на секунды, а не на миллисекунды, и куда сильнее нужны ретраи и изоляция от веб-процесса.

Асинхронная граница стоит там, где надо, но интерфейса у самого сканера пока нет: `scan()` синхронна и получает только имя, размер и MIME, а настоящему сканеру понадобятся байты и `await`. Замена заглушки затронет и сигнатуру, и вызов в `_process` (см. «Что дальше»).

Отвергнутые альтернативы. `BackgroundTasks` выполняется в том же процессе, что и веб-сервер, без durability (задача теряется при рестарте) и без ретраев: строго хуже Celery при той же сложности подключения. Очередь на Postgres (`SKIP LOCKED` и самописный воркер-луп) либо тянет новую зависимость и повторяет функциональность Celery своими руками, либо требует писать и поддерживать собственный планировщик задач с нуля.

### Почему реконсилятор, а не transactional outbox

Постановка задачи в брокер (`process_file.delay(...)`) происходит вне транзакции, которая создаёт запись файла. Если Redis недоступен именно в этот момент, запись остаётся в БД со статусом `uploaded`, таска никогда не ставится, и файл осиротевает молча. Сценарий воспроизведён в `tests/test_failure_modes.py::test_orphan_from_broker_outage_is_reconciled`.

Transactional outbox — правильный продакшен-ответ на эту проблему: писать событие в ту же транзакцию, что и бизнес-данные, и публиковать его отдельным процессом, читающим таблицу-очередь. Но это отдельная таблица, отдельный процесс-публикатор и логика идемпотентности на публикацию.

Периодический подбор зависших записей (`worker/reconciler.py`, `beat` раз в `RECONCILE_INTERVAL_SECONDS`) даёт тот же результат за десятую часть кода: один SQL-запрос по `updated_at` и повторная постановка задачи. Ни одна запись не остаётся в `uploaded`/`processing` навсегда.

### Почему без TanStack Query

Фронтенду нужно два `GET` (файлы, алерты) и один `POST` (загрузка). Кэш между компонентами, дедупликация параллельных запросов и точечная инвалидация — это то, за что платишь сложностью TanStack Query, и на таком объёме экранов она не окупается: без него меньше кода, нет отдельного провайдера в дереве и не нужно тащить клиентскую границу в App Router только ради контекста кэша.

Условия, при которых стоит пересмотреть решение: 5 и более эндпоинтов, одни и те же данные нужны в разных ветках дерева компонентов, появляются оптимистичные обновления, нужна пагинация с кэшем страниц, или поллинг (`shared/lib/useResource.ts`) заменяется на SSE/WebSocket и нужна более сложная синхронизация состояния.

### Что было исправлено

Фиксы, не менявшие ответ клиенту: только внутреннее поведение и потребление ресурсов. Пять изменений самого контракта разобраны в следующем разделе.

- **Загрузка держала файл целиком в памяти.** После перехода на потоковую запись (`storage/local.py`, однопроходные аккумуляторы метаданных в `services/metadata.py`) стократный рост размера файла (3 МБ → 300 МБ) даёт рост кучи процесса `backend` на **0.10 MiB** вместо роста, пропорционального размеру файла.
- **Три Celery-таски вместо одной.** Раньше обработка файла шла цепочкой `scan_file_for_threats → extract_file_metadata → send_file_alert`: три круга через брокер, шесть SQL-стейтментов (три `SELECT`, два `UPDATE`, один `INSERT`) и три отдельных коммита на один файл. Сведено в одну задачу `process_file` (`worker/tasks.py`): один круг через брокер, четыре стейтмента (`SELECT` файла, `SELECT`-проверка дубликата алерта, `UPDATE`, `INSERT`) и один коммит.
- **Исключение в середине цепочки оставляло файл в `processing` навсегда**, без единого алерта: предыдущая реализация не перехватывала сбой соседней таски. Теперь `on_failure` у `process_file` доводит запись до `failed` с `critical`-алертом; реконсилятор дополнительно подбирает записи, зависшие по другим причинам (например, если сама постановка задачи не удалась).
- **`task_acks_late=False` терял задачи вместе с воркером**: если процесс воркера падал во время обработки, Celery считал задачу выполненной и она пропадала безвозвратно. Включены `task_acks_late=True` и `task_reject_on_worker_lost=True`.
- **Result backend копил результаты, которые никто не читал**: задачи Celery не возвращают значений, которые нужны вызывающей стороне (файл обновляется напрямую в БД), поэтому backend только рос без пользы. Отключён (`result_backend=None`).
- **Сборка фронтенда падала** на `COPY --from=builder /app/.env.production ./.env.production`: файла `.env.production` не было в репозитории. Строка удалена из `frontend/Dockerfile`.

### Что изменилось в наблюдаемом контракте API

Задание требует рефакторинг «не ломая бизнес-логики». За весь рефакторинг наблюдаемое поведение API изменилось в пяти местах:

- **`DELETE /files/{id}`** раньше отвечал `500` на любом файле, дошедшем до терминального статуса, потому что у `alerts.file_id` не было `ON DELETE CASCADE`, а алерт создаётся для каждого файла без исключений, так что удалить обработанный файл штатным способом было невозможно в принципе. Теперь — `204`, запись вместе с алертами и байтами на диске исчезает.
- **`POST /files`** при недоступном брокере раньше отвечал `500`, хотя файл уже был записан на диск и строка создана в БД: клиент получал отказ на успешно принятый файл, а запись оставалась в БД осиротевшей навсегда. Теперь — `201`, как и при доступном брокере; недоставленную задачу подбирает реконсилятор (см. «Почему реконсилятор» выше).
- **Промежуточный статус `processing` стал недостижимым.** Раньше `scan_file_for_threats` (первая таска в цепочке, `git show 667effc:backend/src/tasks.py`) ставила `processing_status = "processing"` и коммитила его отдельной транзакцией до того, как поставить следующую таску, и окно было наблюдаемым снаружи, `GET /files/{id}` мог застать файл в этом статусе. Три таски схлопнуты в одну (`worker/tasks.py::_process`), и промежуточное состояние больше не коммитится отдельно: переход теперь только `uploaded → processed | failed`. Восстанавливать `processing` отдельным шагом — платить лишним `UPDATE` и коммитом ради состояния, которое живёт доли миллисекунды и которое клиент всё равно не успевает увидеть.
- **Ветка «файла нет на диске» пропала.** Старый `_extract_file_metadata` при отсутствии байтов на диске ставил `failed`, `scan_details = "stored file not found during metadata extraction"` и критический алерт. Новый `_process` (`worker/tasks.py`) диск вообще не открывает: вся обработка идёт по полям строки и потоковым метаданным, посчитанным ещё при загрузке (`pending_metadata_json`). Поэтому файл, чьи байты пропали с диска между загрузкой и обработкой, дойдёт до `processed`/`clean`, а не до `failed`. Это прямое следствие отказа от повторного чтения файла в воркере, а не отдельное решение.
- **Списки обрезаются на 100 записей по умолчанию.** Старые `GET /files` и `GET /alerts` возвращали все строки без пагинации. Новые дают `Query(100, ge=1, le=500)` (`api/v1/files.py`, `api/v1/alerts.py`): при более чем 100 файлах или алертах клиент, не передавший `limit`/`offset`, не увидит хвост списка. Фронт (`shared/lib/useResource.ts`, `features/file-list/api/filesApi.ts`, `features/alert-feed/api/alertsApi.ts`) `limit`/`offset` не передаёт и постраничной навигации не имеет, так что для пользователя UI это будет выглядеть как «файлы пропали».

Всё остальное — коды ответов на прочих путях, состав полей, тексты `detail`, сортировка списков — не менялось. Это держат характеризационные тесты, написанные **до** начала рефакторинга (`backend/tests/test_api_contract.py`, `test_pipeline.py`): они сняли слепок фактического поведения ещё нерефакторенного кода и с тех пор служат сеткой безопасности.

Ожидания в этих тестах поменялись ровно в одном месте, там, где фиксировался сломанный `DELETE`. Сначала тест переименовали в `test_delete_of_processed_file_fails_with_fk_violation` и заассертили `500` как задокументированный баг. Когда баг починили каскадом, тест вернули к исходному имени `test_delete_removes_file` и ассерту `204`.

### Что дальше

- **`MAX_UPLOAD_SIZE` — не барьер на входе.** Starlette разбирает multipart-тело и складывает загруженный файл в свой временный spool на диске ДО того, как запрос доходит до обработчика; `LocalFileStorage.save_stream` обрывает запись и отвечает `413` только после того, как байты уже приняты. Настоящий барьер против заливки гигантского тела — проверка заголовка `Content-Length` до чтения тела запроса (например, в ASGI-мидлвари, которая обрывает соединение раньше Starlette).

- **У сканера нет собственного шва.** `scan()` — обычная синхронная функция, вызываемая из `_process` напрямую, без протокола и точки внедрения. Настоящему сканеру нужны байты файла, `await` и свои таймауты с ретраями, поэтому подмена заглушки затронет и сигнатуру, и вызывающий код. Правильная форма — протокол `ThreatScanner` рядом с `FileStorage` и внедрение той же зависимостью; сейчас он не заведён сознательно, чтобы не плодить абстракцию под единственную реализацию.

- **`FileStorage` не закрывает транспортный слой.** `path()` возвращает `Path`, который уходит в `FileResponse`; для S3 понадобится либо presigned-редирект, либо `StreamingResponse`, то есть правка маршрута скачивания. Транспортно-нейтральная форма — `open_stream()` вместо `path()`.

- **Транзакцией владеет сервис, но воркер его не переиспользует.** `FileService` коммитит сам и самодостаточен, а `worker/tasks.py` и `reconciler.py` всё равно работают с репозиториями напрямую, дублируя связку «сессия → мутация → коммит». Следующий шаг — общий `UnitOfWork`, одинаково доступный HTTP-маршруту, задаче Celery и CLI.

- **Фронтенд не покрыт тестами.** Тестового раннера в проекте нет. Слоёв четыре, `useResource` написан руками — один render-тест на него окупился бы первым же изменением.
