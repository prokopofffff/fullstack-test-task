## Тестовое задание на позицию Fullstack разработчика (Python + React)

**Вводные:**
1. Здесь представлен MVP проект файлообменника. Он позволяет загружать файлы, проверяет их на подозрительный контент и отправляет алерты;
2. Репозиторий содержит в себе бэкенд и фронтенд части;
3. В обоих частях присутствуют баги, неоптимизированный код, неудачные архитектурные решения.

**Задачи:**
1. Проведите рефакторинг бэкенда, не ломая бизнес-логики: предложите свое видение архитектуры и реализуйте его;
2. (Дополнительно) На бэкенде есть возможность неочевидной оптимизации - выполните ее;
3. (Дополнительно) Разбейте логику фронтенда на слои;

## Архитектура

### Бэкенд (`backend/src`)

```
src/
├── main.py            # сборка FastAPI-приложения: роутеры, CORS, обработчики ошибок
├── api/
│   ├── v1/             # HTTP-роутеры — разбор запроса, вызов сервиса, HTTP-код ответа
│   ├── deps.py          # DI-провайдеры (FastAPI Depends) для сервисов и сессии
│   └── errors.py         # маппинг доменных исключений в JSON-ответы
├── services/           # бизнес-логика: FileService (оркестрация), scanner, metadata
├── repositories/       # единственный слой, знающий SQL/SQLAlchemy
├── domain/             # ORM-модели и enum'ы статусов — общий язык всех слоёв
├── storage/            # FileStorage — протокол + локальная реализация на диске
├── worker/             # Celery: приложение, задачи, реконсилятор зависших файлов
└── core/                # конфиг (pydantic-settings), сессия БД, доменные исключения
```

### Фронтенд (`frontend/src`)

```
src/
├── app/         # Next.js App Router: страница, layout — точка сборки фич в экран
├── features/    # автономный кусок функциональности (api + model + ui): file-list, file-upload, alert-feed
├── entities/    # доменные типы, общие для нескольких фич (File, Alert)
└── shared/      # переиспользуемая инфраструктура без домена: http-клиент, конфиг, форматирование, поллинг-хук
```

### Правило направления зависимостей

Бэкенд: **`api → services → repositories → models`**. Роутер не знает про SQL, сервис не знает про HTTP (исключения — доменные, в `HTTPException` их превращает `api/errors.py`), репозиторий не знает про бизнес-правила. Инфраструктура (`storage/local.py`, брокер Celery) всегда спрятана за протоколом (`storage/base.py:FileStorage`), которым владеет вызывающий слой (`services`), а не наоборот — это позволяет подменить локальный диск на S3, не трогая `FileService`.

Фронтенд: **`shared → entities → features → app`**. Слой видит только то, что находится левее него: `shared` не знает о домене, `entities` не знает о фичах, `features` не знает друг о друге напрямую и не импортируют компоненты соседних фич, `app` только собирает готовые фичи на странице.

### Как запускать тесты

Обычный набор тестов гоняется **внутри контейнера** `backend` — так тесты видят ровно то окружение (БД, переменные), в котором приложение реально работает:

```bash
docker exec backend env UV_NO_DEV=0 uv run pytest tests/ -v
```

`UV_NO_DEV=0` обязателен: `backend/Dockerfile` собирает образ без dev-зависимостей (`pytest`, `ruff`, `mypy` не нужны в проде), и без этой переменной `uv run` откажется ставить их поверх уже собранного окружения.

Тесты отказов (`tests/test_failure_modes.py`) сами останавливают и поднимают `backend-worker`/`backend-redis` через `docker compose`, поэтому их нельзя гонять из контейнера — они запускаются **с хоста**:

```bash
cd backend && uv run pytest tests/test_failure_modes.py -v
```

Тест на память (`tests/test_upload_memory.py`) по умолчанию пропускается — он гоняет заливку файла на несколько сотен мегабайт и меряет прирост кучи процесса `backend` через cgroup, поэтому дорогой и требует `docker compose`. Включается явно:

```bash
docker compose -f docker-compose.dev.yml restart backend
RUN_MEMORY_TEST=1 uv run pytest tests/test_upload_memory.py -v
```

### Почему Celery остался

После оптимизации фоновая обработка файла — это один `UPDATE` (статус, результат скана) плюс один `INSERT` (алерт). Брокер под такую нагрузку формально избыточен. Но убрать его нельзя по двум причинам:

1. `POST /files` наблюдаемо асинхронен — ответ 201 приходит до завершения обработки, и клиент видит промежуточный статус (`uploaded` → `processing` → `processed`/`failed`). Синхронная обработка внутри запроса изменила бы контракт API и сделала бы состояние `processing` недостижимым снаружи.
2. Проверка расширения (`services/scanner.py`) — заглушка на месте настоящего сканера (ClamAV, песочница, внешний антивирусный API), где счёт идёт на секунды, а не на миллисекунды, и куда сильнее нужны ретраи и изоляция от веб-процесса.

Отвергнутые альтернативы: `BackgroundTasks` — тот же процесс, что и веб-сервер, без durability (задача теряется при рестарте) и без ретраев — строго хуже Celery при той же сложности подключения. Очередь на Postgres (`SKIP LOCKED` и самописный воркер-луп) — либо тянет новую зависимость и повторяет функциональность Celery своими руками, либо требует писать и поддерживать собственный планировщик задач с нуля.

### Почему реконсилятор, а не transactional outbox

Постановка задачи в брокер (`process_file.delay(...)`) происходит вне транзакции, которая создаёт запись файла: если Redis недоступен именно в этот момент, запись остаётся в БД со статусом `uploaded`, а таска никогда не будет поставлена — файл осиротевает молча (см. Отказ B в тестах ниже).

Transactional outbox — правильный продакшен-ответ на эту проблему: писать событие в ту же транзакцию, что и бизнес-данные, и публиковать его отдельным процессом, читающим таблицу-очередь. Но это отдельная таблица, отдельный процесс-публикатор и логика идемпотентности на публикацию. Периодический подбор зависших записей (`worker/reconciler.py`, `beat` раз в `RECONCILE_INTERVAL_SECONDS`) даёт тот же результат — ни одна запись не остаётся в `uploaded`/`processing` навсегда — за десятую часть кода: один SQL-запрос по `updated_at` и повторная постановка задачи.

### Почему без TanStack Query

Фронтенду нужно два `GET` (файлы, алерты) и один `POST` (загрузка). Кэш между компонентами, дедупликация параллельных запросов и точечная инвалидация — это то, за что платишь сложностью TanStack Query, и на таком объёме экранов она не окупается: без него меньше кода, нет отдельного провайдера в дереве и не нужно тащить клиентскую границу в App Router только ради контекста кэша.

Условия, при которых стоит пересмотреть решение: 5 и более эндпоинтов, одни и те же данные нужны в разных ветках дерева компонентов, появляются оптимистичные обновления, нужна пагинация с кэшем страниц, или поллинг (`shared/lib/useResource.ts`) заменяется на SSE/WebSocket и нужна более сложная синхронизация состояния.

### Что было исправлено

- **`DELETE /files/{id}` падал с `500`** на любом файле, дошедшем до терминального статуса: `alerts.file_id → files.id` был без `ON DELETE CASCADE`, и удаление файла с уже существующим алертом (а алерт есть у каждого обработанного файла) роняло `IntegrityError`. Добавлен `ondelete="CASCADE"` на внешнем ключе (`domain/models.py`).
- **Загрузка держала файл целиком в памяти.** После перехода на потоковую запись (`storage/local.py`, однопроходные аккумуляторы метаданных в `services/metadata.py`) стократный рост размера файла (3 МБ → 300 МБ) даёт рост кучи процесса `backend` на **0.10 MiB** вместо роста, пропорционального размеру файла.
- **Три Celery-таски вместо одной.** Раньше обработка файла шла цепочкой `scan_file_for_threats → extract_file_metadata → send_file_alert` — три круга через брокер, шесть запросов к БД и три отдельных коммита на один файл. Сведено в одну задачу `process_file` (`worker/tasks.py`): один проход, один `UPDATE`, один `INSERT`, один коммит.
- **Исключение в середине цепочки оставляло файл в `processing` навсегда**, без единого алерта — предыдущая реализация не перехватывала сбой соседней таски. Теперь `on_failure` у `process_file` доводит запись до `failed` с `critical`-алертом; реконсилятор дополнительно подбирает записи, зависшие по другим причинам (например, если сама постановка задачи не удалась).
- **`task_acks_late=False` терял задачи вместе с воркером** — если процесс воркера падал во время обработки, Celery считал задачу выполненной и она пропадала безвозвратно. Включены `task_acks_late=True` и `task_reject_on_worker_lost=True`.
- **Result backend копил результаты, которые никто не читал** — задачи Celery не возвращают значений, которые нужны вызывающей стороне (файл обновляется напрямую в БД), поэтому backend только рос без пользы. Отключён (`result_backend=None`).
- **Сборка фронтенда падала** на `COPY --from=builder /app/.env.production ./.env.production` — файла `.env.production` не было в репозитории. Строка удалена из `frontend/Dockerfile`.
